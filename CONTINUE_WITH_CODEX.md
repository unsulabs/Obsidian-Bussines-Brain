## Real integration acceptance

The following prompt preserves the historical recovery prompt's scope. Use it to accept an installation, migration, or integration change, not for an everyday question.

Continue the Obsidian-Bussines-Brain already installed and connected to this business. This is REAL SOFTWARE INTEGRATION with the existing vault, not a writing task or a new business installation.

Read AGENTS.md, guia/ACEPTACION_REAL_CODEX_INSTANCIA_EXISTENTE.md, and docs/ESPECIFICACION_RED_CONOCIMIENTO_V0_4.md in the master checkout (Spanish operational references).

1. Identify the business's existing vault and master repository. Do not create another vault, copy templates, open explicitly rejected business writing, or assume previous summaries replace sources.
2. Run a Git preflight: branch, SHA, and status. If modified, do not force changes: stop the update and explain how to preserve them. If clean, synchronize to the main commit authorized by the owner and verify the exact SHA.
3. From the updated checkout, run scripts/aceptacion_integracion_local.py with --vault, --salida, and --commit-esperado using the verified local interpreter. The --salida directory must be NEW, private, and OUTSIDE both vault and Git. The program does not modify the business. If it fails, preserve and deliver the ZIP of sanitized results.
4. Check the 16 Bases, D/X, links to authorized sources, and navigation in Obsidian GUI. Use CLI only when functional. Do not mark GUI PASS from filesystem paths.
5. Run the complete test with an entirely fictional, isolated business. Diagnose failures without changing the real vault to fix them.
6. Do not apply Bases migration, D/X revision, relationships, or a Canvas map in the real business. First deliver the report, blockers, and correction plan with backups.
7. Report separately: GitHub code, Mac tests, vault state, Obsidian interface, autonomous Codex, second session, restoration, and second computer; use PASS, FAIL, or NO_VERIFICADO. Attach observed evidence, not an unsupported overall conclusion.
8. Do not write a new D01. Recovering and applying the note architecture needs a separate review after integration validation.

Deliver the sanitized diagnostic ZIP with an interpretation of failures and the next gates, not generic commercial writing.

Do not upload private information to the master repository or contact third parties.
